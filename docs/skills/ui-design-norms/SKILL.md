# UI 設計規範

参照なしに UI を設計すると、生成モデルは決まった失敗をしやすい。色を多用してどこにも目が止まらない画面、状態表示とボタンが同じ形で押せるものが分からない画面、どのボタンが何を起こすか読み取れない画面である。機能が揃っていても、これらは使えない UI になる。以下の規範は、各 OS の HIG、デザインシステム、産業 HMI の規格(ISA-101 / High Performance HMI)、WCAG、Nielsen Norman Group の知見から、その失敗を防ぐ規則を抜き出したものである。UI を設計・実装・レビューするときは、これに従う。

規範どうしがぶつかったときは、安全 > 因果の明確さ > 状態の読み取りやすさ > 見た目の整い、の順に優先する。前の 2 つの違反は誤操作に直結するためである。

出典の URL は `references/sources.md`、トークンの出発点は `references/tokens_example.md` にある。

## 視覚の基調と色

- 画面の基調は無彩色(わずかに青寄りのグレー)にする。平常時に彩度の高い色が出てよいのは、主ボタン、選択中の表示、識別色(グラフの系列など)、異常・注意の表示だけにする。(画面全体が静かなら、異常だけに目が向く。ISA-101、Von Restorff 効果)
- 「正常」「成功」「既定の安全側の設定」を緑で常時塗らない。(正常を色で主張すると、本当の異常が埋もれる。High Performance HMI)
- 1 色に 1 つの意味を割り当て、ほかの意味に使わない。(同じ色が複数の意味を持つと、色から意味を読めなくなる。Apple HIG)
  - accent(青系): 操作できる主ボタン、選択中、フォーカス、リンク
  - success(緑): 動作中、接続中、成功
  - caution(琥珀): 注意、危険が増した状態、上限に制限中、未保存
  - critical(赤): 故障、エラー、通信断、破壊的操作の確認
  - neutral(灰): 停止、未接続、無効などの平常状態
- 赤の塗りは、画面で最も重大な 1 種類(非常停止、破壊的操作の確定)に限る。(赤が複数あると、最も重大なものを見分けられない)
- 色を使った表示には、必ずアイコンか文字を添える。状態は色・形・文字のうち 2 つ以上で区別する。(男性の約 8% が赤緑の色覚異常を持つ。Carbon、Fluent、WCAG 1.4.1)
- 灰色・淡い表示は「無効・非アクティブ・補足」の意味に限る。いま有効な値(設定中の目標値、動作中のモード)を灰色や淡い色で描かない。(淡い表示は、その値が無効だと読まれる)
- 範囲の数字、説明文、ラベルに意味色を付けない。(意味のない色は、意味のある色の効果を薄める)
- 色は役割の名前(トークン)で定義し、画面や部品に 16 進値を直接書かない。(直書きすると同じ意味の色が少しずつずれ、規範を保てない。Material 3 のカラーロール)
- ライトとダークの両方を用意するなら、同じトークンの組を両方で埋める。片方だけで確認しない。
- コントラストは、本文 4.5:1 以上、大きい文字 3:1 以上、部品の境界・アイコン・グラフの線 3:1 以上にする。(WCAG 2.2 SC 1.4.3、1.4.11)
- グラデーション、装飾の影、3D 風の立体表現、正常時のアニメーションを使わない。点滅は未確認の重大な警報 1 か所に限り、2Hz 以下にする。(情報を増やさず注意だけを奪う。High Performance HMI、WCAG 2.3)

## 階層・余白・サイズ

- 画面ごとに「1 番目に見るもの」を決め、それを最も強くする。強弱は大きさより、太さ(Regular / Semibold)と文字色の濃淡(primary / secondary / tertiary)で付ける。(大きさだけで強弱を付けると画面が騒がしくなる。Refactoring UI、Apple HIG)
- 主要な実測値(その画面の目的である現在値。例: 現在の温度)は画面で最も大きな文字にする。目安は本文の 2 倍以上の大きさで、Semibold か Bold。副次の読み値(目標値、ほかの量)はそれより小さく、本文よりは明らかに大きくする。ほかの要素を足すときに読み値を縮めない。(読み値は離れた位置からも一目で読めなければならない。小さく地味な読み値では、画面に目の止まる場所ができない)
- ラベルは薄く、値は濃くして、値を主役にする。値と単位だけで意味が通じるならラベルを省く。(ラベルは最後の手段。Refactoring UI)
- 1 画面の文字サイズは 4〜5 段階まで、太さは 2 段階までにする。本文 14px 前後、最小 12px。斜体と全大文字を使わない。(段階が多いと強弱の関係が読めない。Fluent のタイプランプ、GNOME HIG)
- 数値は等幅数字(tabular figures)で右揃えにする。(値が変わるたびに桁の位置が揺れると読めない)
- 間隔は 4px を単位とする決まったスケール(4 / 8 / 12 / 16 / 24 / 32)だけを使う。スケール外の値(5、7、10)を使わない。(Fluent、Carbon)
- グループ内の間隔をグループ間の間隔より必ず小さくし、2 段階以上の差を付ける。(近接の法則。間隔が曖昧だと区切りが読めない)
- 区画は面の明暗で区切り、枠線は入力欄・表・区切り線に限る。枠の中に枠を置くのは 1 段まで。(枠線の入れ子は、境界線だらけで階層のない画面を作る。Refactoring UI、Fluent のレイヤリング)
- 影はポップオーバー・ダイアログ・トーストのような重なる要素だけに付ける。
- 角丸は 3〜4 種類まで(例: コントロール 4、カード 6〜8、オーバーレイ 8、ピル 全丸、接する辺 0)にする。(Fluent のジオメトリ)
- 標準のコントロールの高さは 32 前後、主ボタンは 40 前後にする。最小のヒット領域は 24×24px 以上にする。(WinUI、WCAG 2.2 SC 2.5.8)
- 頻繁に使う操作は大きく手の届きやすい位置に、緊急の操作は決まった位置に押しやすい大きさで置く。(Fitts の法則)
- 重要なものは上・左(先頭側)に置き、重要な操作や情報をウィンドウの下端に置かない。(下端は画面外に出やすい。Apple HIG)

## 状態と操作の区別(アフォーダンス)

- 「いまの状態」を示す部品と「状態を変える」部品を別にする。状態はバッジ(ピル型、アイコン + 短い語、薄い面)、操作はボタンにする。(両者が同じ形だと、何を押せば何が起きるか分からない。Primer の Label、Atlassian の Lozenge)
- 状態バッジにはホバー反応もポインタの変化も付けない。ボタンより背を低くする。
- 押せる部品には hover・pressed・focus・disabled の 4 状態を必ず用意する。比率を揃える(例: hover 8%、pressed 12% の重ね、disabled 38%)。(反応が揃うと、押せるものが学習できる。Material 3 のステートレイヤー)
- 実行できない操作は最初から無効にし、理由を必ずツールチップか隣の文で示す。理由の無い無効化を作らない。押させてから警告を出さない。(理由が無いと、壊れているのか条件待ちなのかを区別できず、何をすれば押せるかも分からない。GNOME HIG、Fluent 2、Nielsen N5)
- 注意文を枠で囲まない。(枠付きの文は入力欄に見える)
- 1 文字だけのボタン(「0」「x」)を作らない。アイコン + ツールチップか、動詞のラベルにする。(1 文字は値に見える)
- トグルボタンを使うときは、ラベルが「いまの状態」か「押した後の動作」かを曖昧にしない。迷うなら、状態をバッジで、操作を動詞のボタンで出す。
- タブは画面の切り替えだけに使い、モードや状態の選択に使わない。状態の選択はセグメンテッドコントロールかラジオにする。(タブで選ぶと「見ている画面」と「有効な設定」がずれる)
- 選択状態を表す部品(セグメント)と、アクションを実行する部品(クリア、保存)を同じ列に混ぜない。(Apple HIG)
- 2 値の即時反映の設定はスイッチにし、ラベルは名詞にする。(GNOME HIG、NN/g)

## 1 領域 1 主操作

- 強調色のボタン(主ボタン)は 1 つの領域に 1 つまでにする。同格の操作が並ぶときはすべて中立色にする。(GNOME、Fluent 2、Apple HIG)
- 複数の主ボタンが必要に見えるなら、領域の分け方を見直す。
- 状態によって主操作が変わる画面では、主ボタンの位置を固定し、ラベルを状態に合わせて変える。そのときは状態名をボタンの近くに常に表示し、ラベルは必ず動詞にする。(位置が動くと探させる。ラベルだけが変わると、状態の取り違えが起きる)
- 優先度は大きさではなくスタイル(塗り / 枠 / 枠なし)で区別する。(Apple HIG)
- 破壊的な操作でも、その画面の主目的でなければ大きな赤いボタンにしない。控えめに置き、確認の段階で初めて赤くする。(Refactoring UI)
- 状態を後退させる操作(切断、ログアウト)に主ボタンの見た目を与えない。

## レイアウトと情報の出し方

- 全体の状況は、ヘッダーか 1 か所に固定した状態領域にまとめ、どの画面からも同じ場所で読めるようにする。まとめるのは、接続、運転状態(停止 / 運転中など)、現在のモード、警報の有無である。(状態を読むために画面のあちこちを見回させない。Nielsen N1、ISA-101 の Level 1)
- 情報を階層に分ける: 概観(常時)→ 操作対象の操作 → 詳細 → 診断・保守。めったに使わない設定と危険な操作は手前に出さない。(段階的開示。GNOME、Apple、ISA-101 の 4 階層)
- 折りたたむのは、めったに使わないもの・危険なもの、または場所が本当に足りないときだけにする。領域に空きがあるのに、調整でよく使う項目(ゲイン、上限など)を折りたたまない。(隠した項目は存在に気づかれず、開く手間も増える。段階的開示は空いた領域を作るための規則ではない)
- 一度設定すれば済むもの(接続先、ポート、アカウント)は、設定後に小さなチップやメニューに畳み、一等地を明け渡す。
- 同じ情報(操作対象、現在の設定、同じ操作のボタン)を 2 か所以上に置かない。(どちらが正しいかを利用者に考えさせる)
- 頻繁に使う補助操作は、それが影響する値のそばに置く(例: 読み値の横の「原点に設定」)。専用ページの同じ操作は残してよい。(移動の手間が減り、因果が見える)
- 画面の構成は「ナビゲーション / 内容 / インスペクタ」を基本にする。同格のページが 5 個以下なら上部、5〜10 個なら左に置く。(Apple のスプリットビュー、Fluent の NavigationView)
- ヘッダーやツールバーのグループは 3 つまでにする。(Apple HIG のツールバー。グループが多いと毎回全部を読ませる)
- 選択肢を減らすか分ける。ツールバーに 10 個以上の操作、7 個以上のタブ、10 個以上のチェックボックスが並んだら構成を見直す。系列や項目の選択はプリセットで出す。(Hick の法則)
- 内部用語(レジスタ番号、内部 ID、式)は既定で隠し、ツールチップや詳細に置く。詳細度を 2 段(よく使う設定のフォーム / 全項目の表)に分けてよい。(Nielsen N8)
- 消せない複雑さ(モード、ゲイン、上限)は、既定値・プリセット・折りたたみで扱い、利用者に組み合わせを考えさせない。(Tesler の法則)
- 枠を動かさない。通常の操作で入力欄やグラフの位置が跳ばないよう、条件付きで出る行(結果、注記、補足)の場所を常に確保し、値が無いときは淡い「—」を出す。高さが変わってよいのは、利用者が明示的に表示を切り替えたときだけにする。(操作中に対象が動くと、読み取りと操作を誤る)
- 浮動・閉じるボタン付きのドッキングパネルを既定にしない。固定配置 + 幅を変えられる区切りにし、幅を保存して初期化の手段を用意する。(迷わないことを配置の自由度より優先する)
- 最も狭いウィンドウから設計する。最小サイズでも、主要な操作と状態が窓の中に見えるようにする。(GNOME HIG のアダプティブ)
- 大きなウィンドウでは、読む内容(設定、フォーム)に最大幅を設ける。
- 空の画面には、何が無いのか、次に何をすればよいか、そのための主ボタン 1 つを出す。(白紙は、壊れているのか未設定なのかを区別できない)

## フィードバックと通知

- 操作には 400ms 以内に反応する。時間がかかる処理は、押下状態と「処理中」を即座に出し、結果は後から反映する。(Doherty の閾値)
- 通知の種類を使い分ける。

| 種類 | 使う場面 | 消え方 |
|---|---|---|
| バナー | 続いている状態(オフライン、読み取り専用、警報中) | 原因が解消するまで残る |
| トースト | 利用者の操作に対する一時的な結果 | 数秒で消える(ホバー中は残す) |
| インライン | 特定の値や入力に付く注記、入力エラー | 条件が続く間 |
| ダイアログ | 作業を止めて判断させる必要があるもの | 利用者が選ぶまで |
| ログ | 記録として残すもの | 履歴に残る |

- バナーはコンテンツの上に重ねず、レイアウトを押し下げて出す。構成は「アイコン + 見出し + 1 行の説明 + ボタン 1 個まで」にする。(GNOME、Fluent InfoBar、Carbon)
- 異常は、全体の表示(バナーか状態領域)と、原因になった値の局所の表示の両方で示す。局所の表示は、その読み値の面に状態色を薄く敷き(警告は琥珀、故障は赤)、アイコンと文字を添える。色だけにしない。(バナーで「何かが起きた」と分かり、局所の表示で「どの値か」が分かる)
- 説明文や案内で画面上の位置やラベルに触れるときは(「右上の [接続] を押す」)、実際に描画された画面の位置・ラベルと一致させる。(案内と画面が食い違うと、利用者は案内と画面のどちらが正しいかを判断できない)
- 続いている重大な状態のバナーは、原因が解消するまで閉じられないようにする。状態が速く変わっても、1 秒以上は表示を保つ。(Fluent InfoBar)
- エラーや故障をトーストだけで伝えない。(時間で消える通知は見落とされる。Carbon、WCAG 2.2.1)
- 警報(人が対処すべきこと)とログ(記録)を分ける。対処の要らない出来事を警報にしない。(警報が多すぎると読まれなくなる。EEMUA 191)
- 操作の結果は、コマンドの応答(「OK」)ではなく、対象の実際の状態で示す。(応答は成功でも、対象がその後に失敗していることがある)
- 正常時に「問題なし」を大きく表示しない。1 行の淡い文字にとどめる。

## 入力と値

- すべての数値に単位を付ける。内部の単位は 1 系統(SI など)にし、表示単位の切り替えは表示だけで行う。
- 入力欄は右揃え・等幅数字、幅は最大桁数に合わせる。範囲がある値はスライダーと入力欄を併設し、両端の値を淡く表示する。(Apple HIG のスライダー)
- 入力できる範囲は部品の範囲そのもので制限する。範囲外の入力は、その場で理由を示して拒否する。(後から丸めるより、入力の時点で分かるほうが速い。Nielsen N5)
- 値を上限で制限したら、黙って丸めない。元の値・制限後の値・理由を示す(「8.0 → 5.0(上限)」)。(なぜ指示どおりにならないかを利用者が説明できるようにする)
- 指令(目標)と実測(現在値)がある量は、必ず並べて見せる。数値を並べるか、同じ目盛り上に 2 つのマーカーを置く。(差が見えないと、追従しているかを判断できない)
- 計算で出した推定値は、測定値と区別して示す。「推定」のタグと「≈」を付け、式と前提をツールチップに書く。系列名や記録の列名にも推定と分かる名前を付ける。(推定を測定と取り違えると、誤った判断の根拠になる)
- 同じ量に複数の基準があるときは、基準を選べるようにし、解決後の値を示す。例: 回転体の目標を「1 回転内(最短)」と「多回転の絶対値」から選び、入力の下に「→ +401.20 rad へ(+0.83 rad)」を出す。(絶対値の基準しかないと、大きく回った後の「0 へ」で何十回転も戻ることがある)
- 物理的に意味のある値(負のゲイン、ホスト側で計算する補償項)を、安全そうに見えるからという理由だけで入力不可にしない。範囲・注記・保護(暴走したら止める仕組み)を付けて許す。(狭すぎる範囲は、正当な試験を妨げる)
- 既定値へ戻す操作は ↺ アイコン + ツールチップにする。
- 編集中で未適用の値と、適用済みの値と、保存済みの値を区別して示す。行の塗りではなく、状態アイコンと「旧 → 新」の差分、件数で示す。未保存のまま閉じるときは警告する。
- キーボードで値を操作できるようにする(↑↓ で 1 ステップ、Shift で 10 ステップ、Enter で確定、Esc で戻す)。

## 文言

- 用語は 1 つの概念に 1 つの語にする。同じ語を 2 つの意味で使わない(例: 「モード」を対象の状態と設定の種類の両方に使わない)。(Nielsen N4)
- ボタンは動詞で結果を言う(「変更を書き込む」「ID を 5 に変更」)。「OK」「はい」「実行」「適用」だけにしない。(GNOME、Apple、Fluent)
- 止める・消すボタンには範囲を書く(「運転停止」と「全停止」、「この項目を削除」と「すべて削除」)。「停止」「削除」だけにしない。(同じ語が違う範囲の結果を起こすと、因果が読めない)
- 続けてダイアログが開くボタンには「…」を付ける。
- ナビ・タブ・セグメントの項目は名詞にし、長さを揃える。
- 状態はバッジに入る短い語にする(「停止中」「接続中」)。
- 押せない理由は、次に何をすればよいかで書く(「停止すると切り替えられます」)。禁止だけの文にしない。
- エラーは「何が起きたか / 影響 / 次にすべきこと」の 3 点で書き、測定値としきい値を入れる(「温度 136 °C ≥ 135 °C」)。「エラーが発生しました」だけにしない。(Nielsen N9)
- 選択肢の説明は 1 行の平易な文にする(「指定した速度で回り続けます」)。式や内部名は詳細に置く。
- 複数の言語で出すなら、文字列はすべてカタログ経由にし、キーとプレースホルダを全言語で揃える。固定幅の部品(ナビ、セグメント、ボタン)の訳は短く保つ。(訳文の長さの違いでレイアウトが崩れる)
- 説明文は 1 行あたり全角 35〜40 字(欧文 50〜60 字)までにする。
- 日本語の説明文・ツールチップ・ダイアログ本文は、次の文章規範に従う: japanese-tech-writing(https://gist.github.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d)。「なぜそうなっているか」を伝える長めの説明には cognitive-rhythm-writing(https://gist.github.com/k16shikano/eb2929f13ed19c97188393d297be8432)も併用する。

## 確認と破壊的操作

- 確認ダイアログは、不可逆か影響の大きい操作だけに出す。日常の操作と、止める操作には出さない。(確認を出しすぎると、利用者は読まずに押すようになる。NN/g)
- 取り消せる操作には、確認より取り消し(Undo)を用意する。(GNOME HIG)
- タイトルは何が起きるかの質問にする(「ID 1 を 5 に変更しますか?」)。本文は影響と元に戻せるかを、具体的な値で 1〜3 行にする。
- ボタンは具体的な動詞と「キャンセル」にする。破壊的なボタンを既定ボタン(Enter)にしない。Esc は常にキャンセルにする。
- ボタンの並び順は OS の慣習に従う(Windows は実行が左、macOS と GNOME はキャンセルが左)。ツールキットのボタンの役割の仕組みを使い、手で並べない。
- 破壊的なボタンは、ダイアログ内で唯一の色付きボタンにする。
- 本当に危険な操作には、もう 1 段の防止を重ねる。前提条件のチェックボックス(すべて入るまで実行を無効)、対象の名前や ID の入力、長押しで確定(1〜1.5 秒、途中で離せば何もしない。キーボードの代替も用意する)のどれかを使う。
- 影響の大きい操作は「対象を選ぶ → 内容を確認する → 実行する」の順にし、1 操作で実行させない。(Select Before Operate)
- 入力欄の検証エラーにダイアログを使わない。インラインで示す。(Fluent)

## 安全・リアルタイム系の追加規範

装置を動かす、計測値をリアルタイムに表示する、安全に関わる UI では、前の節に加えて次に従う。見た目の誤解が物理的な事故につながるためである。

### 状態モデルと操作

- 状態機械を 1 本に決め、状態ごとに主操作を 1 つだけ見せる(例: 未接続 → 停止中 → 有効 → 運転中、ほかに故障と非常停止ラッチ)。(状態を中心にすると、次に押すものが一意に決まる。ODrive、Siemens Startdrive)
- 許可(有効化)と起動(運転開始)を別の操作にする。(許可だけでは動かないので、誤操作が 1 段減る。IEC 60204-1 のイネーブル装置、TwinCAT)
- 「運転停止(指令を止めて保持)」「無効化(出力を切る)」「非常停止(全体を即座に止めてラッチ)」を別の語と別のボタンにする。
- 主操作は選択中の 1 台にだけ働かせ、全台に働くのは非常停止だけにする。
- 構成の変更(パラメータの書き込み、ID の変更、モードの切り替え)は、停止中だけ許す。それ以外はボタンを無効にして理由を出す。(Dynamixel の EEPROM ロック)

### 非常停止

- 画面上の非常停止はソフトウェアの停止であり、規格上の非常停止装置ではない。物理的な遮断手段の併用を前提にし、そのことをツールチップと解除の画面に書く。(ISO 13850 は、ソフトウェアだけの非常停止を主手段と認めない)
- 非常停止は、すべての画面の同じ位置(ヘッダーの端)に固定し、画面で唯一の赤い塗りのボタンにする。キーの表示をボタンに添える。すぐ見つかり、ほかと見間違えない形にする。
- 非常停止を平常時の画面で最も目立つ要素にしない。ほかのボタンと区別できる程度の大きさ(標準のボタンより一回り大きい程度)にとどめ、主要な読み値より目立たせない。(平常時に最も目立つものは、読み値と警報から視線を奪う)
- 警報・故障が発生しているときは、そのバナーを画面で最も目立つ要素にする。面積とコントラストの両方で非常停止を上回らせる。(異常時に利用者が最初に読むべきなのは、何が起きたかである。非常停止の位置は固定なので、目立たせなくても見つけられる)
- 警報・故障の表示を、非常停止と同じ形・同じ塗りにしない。赤い塗りのピルを赤い塗りのボタンの隣に置くと、2 つ目のボタンに見える。警報はアイコン + 文字、枠か薄い面、ボタンと違う形(全幅の帯、左端の色帯)で示す。
- 押した瞬間に作動させる。確認も長押しも求めない。(誤って押しても止まるだけで、安全側である)
- キーを割り当てる。ほかの用途と衝突しないキーは常に非常停止にし、モーダル・入力欄の中でも働かせる。Esc のように取消にも使うキーを割り当てるなら、動き得るものがあるときだけ非常停止にし、それ以外では通常の取消として働かせる。(何も動いていないときの取消で非常停止がかかると、毎回解除を求められる)
- 押したらラッチする。全体に赤いバナーを出し、新しい指令・周期送信・自動シーケンスをすべて止め、受け付けない。拒否は画面だけでなく処理側でも行う。
- 解除は 2 段階(解除ボタン → 安全確認のチェック付きダイアログ)にする。解除しても自動で再始動させず、すべて停止中に戻す。(ISO 13850。解除は再始動の許可であって、再始動ではない)
- 停止のしかた(即座に出力を切る / 減速してから切る)を決め、設計書に書く。重力負荷がかかる装置では、即座に切ると落下するおそれがある。(IEC 60204-1 の停止カテゴリ 0 / 1)

### 出力段階・危険の増した状態

- 出力を 2 段階に分ける装置では、安全側を無彩色の既定にし、危険側だけに琥珀の持続表示(閉じられないバナー + アイコン + 文字)を付ける。危険側に赤を使わない。(赤は非常停止と見分けられなくなる)
- 危険側への切り替えは、停止中であることと、前提条件のチェック(固定した、周囲に人がいない、電源を切る手段が手元にある)を求める。
- 切断・通信断・非常停止・再起動のあとは、自動で安全側に戻す。
- 現在の上限は、入力の近く(スライダーの範囲、ゲージの帯)に示す。UI 側の上限と装置内の上限が別にあるときは、実効の上限(小さいほう)を示す。

### 押している間だけ動く操作

- 押している間だけ動くボタンは、クリックするボタンと見た目を変える(枠 + 押下保持のアイコン、押下中だけ塗り)。同格の 2 方向のボタンを両方強調色にしない。
- 指を離した、ポインタが外れた、フォーカスを失った、ウィンドウが非アクティブになった、通信が途絶えた、のどれでも即座に止める。
- 押下中は継続の指令を周期的に送り、装置側に短いタイムアウトを設定する。(UI が固まっても装置が止まる。デッドマン)

### 通信断・読み出し専用・シミュレーション

- 通信の途絶を検知したら、赤いバナーと「再接続」を出し、すべての対象を未接続として表示する。装置側のタイムアウトと UI 側の監視の両方を持つ。
- 読み出し専用(記録の再生など)とシミュレーションは、閉じられない表示で常に示す。読み出し専用では操作を無効にし、処理側でも拒否する。(実機との取り違えを防ぐ)

### 故障・警報

- 正常時に故障ビットをランプの羅列で表示しない。正常時は 1 行、発生時は該当項目だけを示す。全ビットの一覧は診断画面に置く。(High Performance HMI)
- 警報には状態を持たせる: 発生中・未確認 / 発生中・確認済 / 復帰・未確認。優先度は 2〜3 段にし、色・形・文字で区別する。(ISA-18.2)
- 1 件の警報に、発生時刻、対象、名称、測定値としきい値、考えられる原因、対処、リセットの手段を持たせる。繰り返しは件数でまとめ、最初に発生したものを示す。
- リセットは原因が残っていれば失敗させ、理由を示す。成功しても停止中に戻すだけで、自動で再開しない。

### リアルタイムグラフ

- 1 つのグラフに 1 つの物理量を描き、縦に積んで時間軸を共有・同期させる。右端を現在にする。(PlotJuggler、オシロスコープの Roll モード)
- 複数の対象(装置・チャンネル)を同じグラフに重ねるときは、色で対象を表し、線種で指令・目標(破線)と実測(実線)を分ける。(物理量はグラフの分割ですでに分かれている。オシロスコープのチャンネル色)
- 対象が 1 つだけのときは、色で量の役割を分ける。実測、目標、上限・保護の線にそれぞれ別の色を割り当て、目標は破線のままにする。(色が 1 色だけだと、線種の違いしか手がかりがなく、一目で区別できない)
- 系列の色に、状態色(赤・琥珀・緑)と accent を使わない。同じ対象の色を、凡例・最新値の表示・状態のチップで共通にする。(Keysight、Saleae)
- 系列の色は、対象が登録された順に固定の枠で割り当てる。ID などの番号から計算しない。ほかの対象が増減しても塗り替えない。(番号の剰余で決めると、別の対象が同じ色になることがある)
- 格子は横線だけ、ごく薄くする。各グラフの左上に量と単位、右端に最新値を対象の色の印と文字で出す。(直接ラベルは、色の区別が難しい場合の識別手段になる)
- すべての軸に量と単位の題(「温度 [°C]」「時間 [s]」)を付ける。目盛りは 1・2・5 の倍数のきりのよい値に置き、端数の目盛り(-4:10、-3:20 など)を作らない。(題の無い軸は何の値か分からず、端数の目盛りは読み取りを遅くする)
- 上限・目標・保護のしきい値のような重要な基準線は、常に見えるようにする。自動スケールでも基準値を軸の範囲に含めるか、範囲外にあることを示す印(軸の端の矢印と値)を出す。自動スケールで基準線を画面から消さない。(基準線が消えると、値が上限にどれだけ近いかを判断できない)
- 基準線は、値が離れている間は細く淡く描き、値が近づいたとき・超えたときに強調する(太く、状態色に)。系列の色を基準線に使わない。(常に明るい基準線は平常時に視線を奪い、系列と同じ色の線はデータと見分けられない。ISA-101 の「異常に近づいたときだけ目立たせる」)
- 系列の選択はプリセット(用途別の組)で出し、チェックボックスを並べない。
- 一時停止(受信は続ける)、全グラフで同期するカーソル、2 点の差(Δt・Δ値)、単発のトリガ取得を用意する。(Saleae、PlotJuggler、オシロスコープ)
- 状態・モード・制限の発生区間を、グラフの下に時間軸を揃えた帯で示す。帯には文字を入れる。(いつ何をしたら何が起きたかが残る。Grafana の State timeline)
- 値が不連続に跳ぶ点(原点の再設定、角度の折り返し)では線を切る。縦線で結ばない。(実際には起きていない急激な変化に見える)
- 縦軸の自動スケールにはヒステリシスを付け、小さな変化で軸を揺らさない。
- 描画の更新は 30〜60 fps に抑え、受信の頻度と切り離す。
- 温度のような遅い量は、主要なグラフではなく数値の表示で足りることが多い。

## 検証の規範

- 見た目は、描画した実際の画面(スクリーンショット)で確かめる。コードを読んだだけで判断しない。(色の組み合わせ、文字の切れ、間隔は、描画しないと分からない)
- 確かめる条件: 最小のウィンドウサイズ、ライトとダークの両方、UI のすべての言語、平常時と異常時(警報、制限中、通信断、空の状態)。
- 中身が最大になった状態(項目が最大数、最も長い文字列と注記が出た状態)でレイアウトを確かめる。
- 平常時の画面で、彩度の高い色が「視覚の基調と色」の許容範囲に収まっていることを確かめる。
- 目立ち方は、人の見え方で判定する。要素が揃っているかを順に点検するだけで済ませない。たとえば、ぼかすか縮小したスクリーンショットで最も目立つ 2〜3 か所が最も重要なものか、1 秒ほど見たときに最初に目が行く場所はどこか、を問う。(生成モデルは画面のすべての要素を同じ注意で読むので、情報が密で強弱の均一な画面を高く評価しやすい。人は強弱の階層が無いと視線の止まる場所が無く、目が滑る)
- 情報量の多さを評価の加点にしない。
- 異常時の場面では、警報のバナーと原因の値が画面で最も目立ち、平常時の場面では主要な読み値が最も目立つことを確かめる。非常停止がどちらの場面でも最も目立っていないことを確かめる。
- 押せるものと押せないものが見た目で区別できること、各領域の主ボタンが 1 つ以下であることを確かめる。
- コントラストと色の区別は、目視ではなく計算で確かめる(WCAG のコントラスト比、色覚シミュレーションでの色差)。
- 通常の操作(開始する、結果が出る、制限がかかる)で、レイアウトの位置が動かないことを確かめる。
- 確かめてから利用者に見せる。

## 実装で起こりやすい落とし穴

- レイアウトの最小サイズは、UI に中身が入った後で測る。起動直後の空の状態で測った値は小さすぎる。
- ヘッドレスの描画環境(オフスクリーン、CI)にはフォントが無いことがある。代替フォントで測った幅や高さは実際と大きく違うので、フォントを読み込むか、その測定を行わない。
- 半透明色の表記(`rgba(...)`)は、描画 API によって解釈されず黒や透明になることがある。トークンを渡す前に、その API が受け付ける形に変換する。
- スタイルを属性で切り替える仕組みでは、属性を変えた後にスタイルの再評価が必要なことがある。変えたのに見た目が変わらないときは、再評価を疑う。
- テスト環境では、破棄を遅延させた部品がイベントループの不在で溜まり続け、テーマの再適用などが次第に遅くなることがある。テストの後始末で確実に破棄する。
- DPI のスケーリングは測定値と撮影結果を変える。比較する画面は同じ倍率で撮る。
- OpenGL などの独自描画の部品は、通常の画面キャプチャに写らないことがある。
